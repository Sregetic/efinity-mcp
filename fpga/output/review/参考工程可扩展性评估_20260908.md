# Ti60 / SC431HAI 参考工程可扩展性评估

日期：2026-09-08。评估对象：摄像头至 HDMI/LCD 示例对缩放、裁剪、帧操作、边缘算法及 RISC-V/AI 集成的支撑程度。

## 结论

现有资料足以作为相机接收、DDR 控制和显示输出的复用起点，但不是已具备全部后续能力的可编程视觉平台。HDMI V6 和 CSI→DSI V3.5 的核心仍为固定格式视频扫描输出。建议保留外设驱动，改造帧访问与处理调度层；不建议围绕现有顺序帧读出逻辑不断叠加特例。

数字放大与 DVP/MIPI 接口类型没有必然限制关系。若上一套 DVP 工程没有可控的取图地址、行缓存重用和输出节拍适配，确实容易在缩放处受阻；本次未检查旧 DVP 工程，因此不对其历史根因下结论。

## 2. 已确认的重要事实

### E1：当前链路先存 RAW，再去 Bayer

HDMI V6 `rtl/ti60f225_oob_top.v:537-574`：帧缓存输入 32 bit，来自四个 RAW10 像素各取高 8 bit；输出 16 bit，即两个 RAW8 像素。`733-750` 再调用 `debayer_top_2to1` 生成两像素 RGB。

因此当前路径为：CSI 接收 → RAW10 截取高位形成 RAW8 → DDR 帧缓存 → RAW8 双像素扫描输出 → 去 Bayer → RGB 输出适配 → HDMI。此前仅依据目录列出的抽象链路不代表这个实际顺序。

结论：在此处插入一般 RGB 缩放算法需要先处理格式边界。直接对 Bayer 样本任意重复、插值或改变裁剪奇偶位置，会影响其颜色相位。首版推荐在去 Bayer 后进行显示缩放；若仍保留 RAW 帧缓存，ROI 读出需保留邻域和 Bayer 相位。

### E2：960 是双像素工作单位，不是自动缩放

同一顶层 `255-263` 固定目标 1920×1080；`547-548` 配置 `MAX_VID_WIDTH=960`、`MAX_VID_HIGHT=1080`，`568` 的水平有效周期为 `MAX_HRES/2`。结合 16 bit RAW8 输出，这表示一拍两个像素，而非将 1920 像素缩成 960 像素。

更改 H_VALID/V_VALID 只会改变扫描长度；若取样地址仍顺序递增，不会自动产生图像缩放。当前没有可配置的源坐标映射、横纵相位累加器或插值接口。

### E3：另一个包的 Zoom 注释对应裁剪逻辑

奥唯思包 `07-FPGA_HDL_Image-2023.2/03-1_Ti60_SC130GS_MIPIx4_HDMI_1280720/src/Sensor_Image_XYCrop.v:118-132` 用水平/垂直坐标范围限定输出 href，而像素数据仅打一拍传递。它是居中裁剪，不会重复像素、重复行或插值；裁剪出的区域要铺满输出窗口仍需独立 scaler。

### E4：固定分辨率限制分布在多处

相机配置 ROM `rtl/cam_i2c_ctrl/i2c/i2c_master_reg_rom.v:236-239` 设置输出 0x0780×0x0438，即 1920×1080。顶层显示时序、帧缓存容量、读出打包都与该模式相关。

`rtl/debayer/debayer_top_2to1.v:73-78` 将行地址计数宽度设为 10。当前每拍处理两个 Bayer 样本；若直接扩成 2560 像素一行，需要 1280 个双像素地址，超过 10 位地址容量。全幅 2560 模式需要一起检查行缓存、计数、帧地址与时钟，而非只改相机寄存器。

HDMI V6 SDC 将接收像素时钟设为 50 MHz。按每拍四像素，即使每拍均有效，上限也为 200 Mpixel/s；2560×1440×60 的有效像素需求约 221.18 Mpixel/s，已超过这个配置上限。这是当前参数的算术上界，不是实测吞吐。

### E5：DDR 是真实可复用基础，但帧管理不是通用任务系统

顶层采用三帧缓存。DDR 控制参数为 16 位物理数据、128 位 AXI 数据；当前只有一套视频帧缓存读写路径直接连接控制器。现有帧切换面向连续采集和扫描显示，没有现成的任意 ROI/stride 请求接口、软件帧描述符、多读者引用或 AI 任务队列。

保留 DDR 控制器与经过验证的 CDC/FIFO 基础，在其上增加受控的帧地址、读者生命周期、行级读取和仲裁。冻结显示、AI 持有帧以及 Canny 中间结果需要明确分配，避免读者未结束时帧被覆盖。

### E6：工程内存在 SoC 文件，不代表已集成 RISC-V

HDMI V6 文件夹含 `rtl/soc_oob/top_soc_oob.v`，但主 XML 的活动设计文件列表没有该文件或其他 SoC 源码，顶层也没有运行中的 RISC-V 实例。CSI 的寄存器 AXI 接口在顶层 `413` 行起被接为常量。DSI V3.5 活动源码同样未接入 SoC。

RISC-V/TinyML 需要独立集成：SoC、控制寄存器、DDR 地址规划、DMA/总线仲裁、缓存一致性、模型与软件。它不是开启一个现有配置项即可完成。

### E7：版本与约束要先整理

HDMI V6 XML 标注 Efinity `2026.1.132.1.2`；实际活动 CSI 源文件 `rtl/csi_rx_controller.sv` 标注生成工具 `2025.2.288.4.15`、IP `5.15`。目录下另一个 IP settings 文件标注 `5.16`，但主工程引用的是前者。后续应尊重活动源码列表并确认相机同步表现，避免批量重新生成 IP 后悄然替换实现。

HDMI V6 活动 SDC 第 86 行、DSI V3.5 活动 SDC 第 80 行均包含未注释的 `create_clock -period <USER_PERIOD>`。它们不是可直接接受的完整时钟约束。需要按实际时钟补齐并复核时钟关系，再建立当前工具下的编译基线。

## 3. 功能支撑程度

### E8：三帧切换同拍请求的局部 RTL 反例已复现

`rtl/frame_buffer_V3/bank_switch.v:116-117` 分别应答读写请求边沿，但 `131-144` 的状态更新采用写优先 `if ... else if`。当已有待显示完成帧且新的读写请求同拍到达时，读请求得到 ACK，却未进入读切换分支。

使用未修改的原模块与 Icarus Verilog 进行最小仿真：先提交一帧，形成 `clean_bank=0, rd_bank=1`；普通读请求将 `rd_bank` 切到 0；同样起始状态下同时提交读写请求，得到 `wr_ack=1, rd_ack=1, rd_bank=1, clean_bank=0`。因此“ACK 等于已经完成对应切换”的接口语义在此场景不成立。局部仿真没有证明某块实物上发生的频率，也不等于整个视频系统已仿真。

调用端的读写请求来自独立的读/写状态机，未见互斥处理；`bank_sw_ack` 在两个子控制器中仅声明，没有用于等待应答。建议将读写并发更新统一计算，或显式保留未服务的请求并在真正处理后应答。修复应在主工程选定后进行，本轮保留原源码。仿真源文件与日志保存在本报告同目录的 `bank_switch_probe`。

### E10：顶层帧参数并未全部下传

`frame_buffer_V3/frame_buffer.v:186-193` 实例化 `ddr_buffer` 时遗漏 `FB_NUM`、`MAX_VID_WIDTH`、`MAX_VID_HIGHT` 参数，因此下层仍使用自己的三帧、1920×1080 默认配置。顶层把宽度设为 960，并没有同步改变 bank 地址规划；只改顶层帧数同样不会修改下层切换逻辑。

当前下层按 32 bit 输入宽度计算静态 bank 步长：`1920*1080*4+0x200=0x7e9200`。动态传输长度另由有效拍计数形成，二者不是统一配置源。注意 960 指输出双像素拍数；1920×1080 RAW8 的有效帧字节数为 2,073,600，而非 960×1080×4。扩展分辨率、像素格式或 AI 地址区前，应统一像素数、每拍像素数、stride 和帧容量的单位与传递关系。

### E9：LCD 参考例程含两个 DSI 发送实例

DSI V3.5 顶层 `814-949` 将同一 RGB 流接到两个 `dsi_tx_top` 实例，分别连接不同端口。若实物仅使用一个面板，集成时应按实际需求精简第二路及接口配置；代码中的双 DSI 复制不等于已完成 HDMI+DSI 双输出的整合，也不应直接沿用其资源占用作为单屏最低需求。

| 功能 | 现状 | 下一步 |
|---|---|---|
| SC431HAI 接收、基础彩色输出 | 有明确顶层、初始化、去 Bayer 和输出路径 | 匹配实物接口，建立上板基线 |
| LCD / HDMI 独立输出 | 各有示例 | 分别验证；双输出另做带宽/时序集成 |

| 真正放大/缩小、任意 ROI | 当前目标视频工程没有完整实现 | 源坐标映射、行读取重用、插值与独立输出时序 |
| 冻结、回放、多帧对比 | 有三帧缓存基础，不等于这些功能已实现 | 帧保留/释放、选择、队列及显示合成 |

## 4. 推荐的改造边界

保留：板级接口、相机 I²C 配置/接收、DDR 控制与校准、显示发送器、可验证的去 Bayer 模块。

重点改造：帧读写调度、像素格式边界、源/目标尺寸解耦、ROI 取图、显示合成与运行时配置。不要为了复用而强行保留阻碍后续功能的固定扫描框架。

建议目标结构：

```
相机接收 → 解包/去 Bayer → 统一像素流 → 帧写入
                                      ↓
                              帧管理 + DDR 仲裁
                               ↙             ↘
                       ROI/行读取           算法/AI取图
                            ↓                  ↓
                       缩放/插值         Canny/几何/TinyML
                            ↓                  ↓
                       显示合成 ← 同帧关联结果
                            ↓
                         HDMI / DSI
```

这是目标设计，不是当前拓扑。若优先保留低带宽 RAW 缓冲，也可将去 Bayer 放在受控的源行读出之后；两种策略只选一种作为实现主线，避免重复维护两套系统。

## 5. 图像缩放应当成为最早的扩展验收

先用带坐标/棋盘格的固定测试帧证明寻址，再接摄像头。建议顺序：

1. 在固定 1920×1080 输出时序下，将源图中心 960×540 区域放大铺满；先最近邻，再评估双线性。
2. 改变 ROI 起点并验证移动，确保使用源图 stride，而不是把 ROI 当作紧密连续整帧。
3. 验证 1280×720 到 1920×1080 的非整数倍率，及缩小输出。
4. 验证冻结帧在采集继续时保持不变；边界 ROI 和跨 DDR burst/行边界时没有错行。
5. 以上成立后再接 Sobel/Canny、最后接 RISC-V/AI。

最近邻示意：`src_x=x0+floor(dst_x*roi_width/out_width)`，`src_y=y0+floor(dst_y*roi_height/out_height)`。双线性需要邻行邻列和定点权重；缩小时还应评估抗混叠。有效实现通常重用源行缓存，避免每个输出像素都进行多次随机 DDR 访问。

数字放大是在固定显示区域中扩大目标，不恢复传感器未采到的细节，也不等于改变屏幕的物理分辨率。

## 6. 带宽与 AI 集成边界

按 1920×1080、60 帧/秒，仅算有效像素的一次写入与一次读取：

| 缓冲格式 | 基础读写带宽 |
|---|---:|
| RAW8 / Gray8 | 248.832 MB/s |
| RGB565 | 497.664 MB/s |
| RGB888 | 746.496 MB/s |

数值为公式预算；未包含额外结果图、AI 张量、Canny 随机访问、刷新与仲裁开销。当前 DDR 参数对应理论峰值 1.6 GB/s，实际可用值需组合负载测量。固定输出大小的局部放大不必增加输出像素总量，但会改变源行重用和取图模式。

逻辑资源与 M10K 还需要当前工程的综合/P&R 报告。易灵思官方 FAQ 某 Ti60 YOLO 参考设计为 57,100 XLR、239 M10K，说明现成全套 TinyML 演示可能占据大量资源，不应仅凭“Ti60 有 DSP”推断所有模块同时适配。应按实际小模型选加速算子，分别检查资源、激活内存和端到端时延。
